# ADR 0005: Better Auth for authentication only

- Status: Accepted
- Date: 2026-10-18

## Context

The app needs email/password login, database sessions, logout, rate limiting, and later optional TOTP 2FA, all self-hosted with no third-party identity provider required. Facts checked on 2026-10-18:

- `next-auth` stable is 4.24.15. v5 never left beta. Since September 2025 Auth.js has been maintained by the Better Auth team in security-patch mode (Auth.js GitHub discussion #13252), and they recommend Better Auth for new projects.
- `better-auth` latest is 1.7.10. Its peer ranges include `next ^14 || ^15 || ^16`, `react ^18 || ^19`, `drizzle-orm ^0.45.2 || >=1.0.0-rc.1 <2`, and `pg ^8`.
- Better Auth's Next.js docs: mount `toNextJsHandler(auth)` at `app/api/auth/[...all]/route.ts`, and add the `nextCookies()` plugin last so Server Actions can set cookies. Read the session with `auth.api.getSession({ headers: await headers() })`. The cookie-only `getSessionCookie` check "does not validate" the cookie and is only for optimistic redirects in `proxy.ts`.
- Better Auth published a security update in July 2026, so advisories must be tracked.

## Decision

Use **Better Auth 1.7.x** for **authentication only**: identity, credentials, sessions, rate limiting, and later 2FA.

- Email and password only. **Public sign-up is disabled.** Accounts are created by an admin, and the first admin is created by a CLI bootstrap script. (`disableSignUp` is expected in Better Auth's email/password options; Phase 3 verifies it against the installed version.)
- Database-backed sessions in PostgreSQL through the Drizzle adapter. Cookies are `HttpOnly`, `Secure` in production, and `SameSite=Lax`.
- Built-in rate limiting is enabled for auth endpoints with database storage, so limits hold across restarts and instances.
- **Authorization is not delegated to Better Auth.** Roles, permissions, and scopes live in ProcureFlow tables and code (ADR 0006). Better Auth's admin plugin role field is not used for access decisions.
- ProcureFlow keeps its own `user_profiles` row per user (status, department). A deactivated profile blocks access even if a session row still exists, and deactivation also revokes all of that user's sessions.
- Session validation happens in the server-side request context used by every page, action, and route handler. `proxy.ts` only does optimistic redirects.

## Alternatives considered

- **Auth.js v4 / v5 beta.** Rejected: v4 is in maintenance, v5 is still beta, and its own maintainers point new projects to Better Auth.
- **Hand-rolled sessions** (cookie plus `sessions` table plus argon2). Rejected: more security-critical code to own (timing-safe comparison, rotation, rate limiting) with no added value.
- **External IdP (Keycloak, Auth0, Clerk).** Rejected for v1: an extra service or vendor for a self-hosted open-source app. OIDC SSO is a later, optional phase.

## Consequences

- Better Auth owns its tables (`user`, `session`, `account`, `verification`). Their Drizzle schema is generated by its CLI and committed. Upgrades must re-check schema diffs.
- Track Better Auth advisories through Dependabot and GitHub security advisories.

## Verification

- Phase 3 tests: sign-up endpoint rejected; login rate-limited after N failures; cookie flags asserted in E2E; deactivated user loses access on the next request; logout invalidates the session server-side.
